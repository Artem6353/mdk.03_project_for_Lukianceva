Тестирование ПО

Вопросы для подготовки к экзамену • 37 вопросов с подробными ответами

Жизненный цикл программного продукта (ЖЦ ПО) — это период времени, который начинается с момента принятия решения о необходимости создания программного продукта и заканчивается в момент его полного изъятия из эксплуатации.

ЖЦ ПО включает следующие основные этапы:

  • Анализ требований — определение функциональных и нефункциональных требований к системе
  • Проектирование — разработка архитектуры и детального дизайна системы
  • Реализация (кодирование) — написание программного кода
  • Тестирование — проверка соответствия продукта требованиям
  • Внедрение — развертывание системы в производственной среде
  • Сопровождение — поддержка, исправление ошибок и внесение изменений
  • Вывод из эксплуатации — завершение использования продукта

Основные модели ЖЦ ПО:

1. Каскадная (Waterfall) модель

Последовательная модель, где каждый этап начинается после завершения предыдущего. Этапы: требования → проектирование → реализация → тестирование → внедрение → сопровождение.

2. Итеративная модель

Разработка происходит циклами (итерациями), каждая итерация включает все этапы разработки и добавляет новую функциональность.

3. Спиральная модель

Комбинирует итеративный подход с элементами каскадной модели, добавляя анализ рисков на каждом витке спирали.

4. Инкрементная модель

Система разрабатывается и поставляется частями (инкрементами), каждая часть добавляет новую функциональность.

5. V-образная модель

Расширение каскадной модели, где каждому этапу разработки соответствует этап тестирования.

6. Agile (гибкие методологии)

Семейство методологий, ориентированных на адаптивность, частую поставку рабочего ПО и тесное взаимодействие с заказчиком (Scrum, Kanban, XP).

Общие принципы моделирования ЖЦ ПС:

  • Декомпозиция — разбиение процесса на отдельные этапы и работы
  • Последовательность и параллельность — определение порядка выполнения работ
  • Итеративность — возможность повторения этапов
  • Верифицируемость — проверка результатов каждого этапа
  • Управляемость — контроль и мониторинг процесса

Классическая водопадная модель (Waterfall):

  • Особенности: строгая последовательность этапов, возврат к предыдущим этапам затруднен
  • Преимущества: простота планирования, четкая документация
  • Недостатки: негибкость, поздняя проверка работоспособности

Спиральная модель ЖЦ ПС:

  • Особенности: четыре квадранта - планирование, анализ рисков, разработка, оценка
  • Преимущества: ранний анализ рисков, гибкость, прототипирование
  • Недостатки: сложность управления, требует экспертизы в анализе рисков

Модель быстрой разработки приложений (RAD):

  • Особенности: короткий цикл разработки (60-90 дней), активное использование CASE-средств
  • Фазы: бизнес-моделирование, моделирование данных, моделирование процессов, генерация приложения, тестирование
  • Преимущества: быстрая поставка, активное участие пользователей
  • Недостатки: подходит не для всех проектов, требует высококвалифицированной команды

Основные принципы тестирования:

  • Тестирование демонстрирует наличие дефектов — невозможно доказать отсутствие ошибок
  • Исчерпывающее тестирование невозможно — проверка всех комбинаций непрактична
  • Раннее тестирование — чем раньше найдена ошибка, тем дешевле её исправить
  • Скопление дефектов — большинство ошибок концентрируется в ограниченном числе модулей
  • Парадокс пестицида — повторяющиеся тесты теряют эффективность
  • Тестирование зависит от контекста — подход зависит от типа приложения
  • Заблуждение об отсутствии ошибок — даже работающее ПО может не соответствовать требованиям

Основные принципы отладки:

  • Воспроизводимость — способность повторить ошибку
  • Изоляция — локализация участка кода с ошибкой
  • Упрощение — минимизация условий воспроизведения
  • Систематический подход — использование методов поиска (бинарный поиск, обратное прослеживание)
  • Документирование — фиксация найденных проблем и решений

Цели тестирования:

  • Обнаружение дефектов в программном обеспечении
  • Проверка соответствия требованиям
  • Повышение качества и надежности ПО
  • Предоставление информации о состоянии продукта
  • Снижение рисков при эксплуатации

Задачи тестирования:

  • Проверка функциональности согласно спецификации
  • Выявление отклонений от ожидаемого поведения
  • Проверка производительности и стабильности
  • Оценка удобства использования
  • Проверка совместимости с различными платформами

Основные этапы тестирования:

  • 1. Планирование — определение стратегии, ресурсов, сроков
  • 2. Проектирование тестов — создание тест-кейсов и тестовых данных
  • 3. Подготовка тестовой среды — настройка окружения
  • 4. Выполнение тестов — запуск тестов и фиксация результатов
  • 5. Анализ результатов — оценка найденных дефектов
  • 6. Отчетность — документирование и представление результатов

Тестовый цикл (Test Life Cycle):

  • Анализ требований
  • Планирование тестирования
  • Разработка тестовых сценариев
  • Настройка тестового окружения
  • Выполнение тестов
  • Завершение тестирования (closure)

Критерии тестирования — это количественные и качественные показатели, которые определяют достаточность тестирования и момент его завершения.

Критерии входа (Entry Criteria):

  • Доступность тестовой среды
  • Готовность требований и спецификаций
  • Наличие тестовых данных
  • Готовность сборки для тестирования
  • Доступность необходимых ресурсов

Критерии выхода (Exit Criteria):

  • Выполнение всех запланированных тестов
  • Достижение требуемого покрытия кода/требований
  • Отсутствие критических дефектов
  • Процент пройденных тестов соответствует целевому значению
  • Соответствие показателей качества установленным нормам

Количественные критерии:

  • Процент покрытия кода (code coverage)
  • Процент покрытия требований
  • Плотность дефектов (дефекты на 1000 строк кода)
  • Процент успешно выполненных тест-кейсов

1. Покрытие (Coverage):

  • Покрытие кода (строк, ветвей, условий)
  • Покрытие требований
  • Покрытие функциональности

2. Метрики дефектов:

  • Количество обнаруженных дефектов
  • Плотность дефектов
  • Распределение дефектов по приоритету/серьезности
  • Скорость обнаружения и исправления дефектов

3. Эффективность тестирования:

  • Процент пройденных/провалившихся тестов
  • Время выполнения тестов
  • Коэффициент повторного открытия дефектов
  • Процент автоматизированных тестов

4. Качественные параметры:

  • Надежность (MTBF - среднее время между отказами)
  • Производительность (время отклика, пропускная способность)
  • Удобство использования, совместимость, безопасность

По уровню тестирования:

  • Модульное (Unit) — тестирование отдельных компонентов
  • Интеграционное — проверка взаимодействия компонентов
  • Системное — тестирование системы в целом
  • Приемочное — проверка готовности к передаче заказчику

По объекту тестирования:

  • Функциональное — проверка функций согласно требованиям
  • Нефункциональное — производительность, безопасность, удобство
  • Структурное — проверка внутренней структуры

Специализированные виды:

  • Регрессионное — проверка после изменений
  • Дымовое (Smoke) — базовая проверка основной функциональности
  • Санитарное (Sanity) — быстрая проверка конкретной функциональности
  • Исследовательское — творческий подход без формальных тест-кейсов
  • Нагрузочное — проверка поведения под нагрузкой
  • Стресс-тестирование — проверка на пределе возможностей
  • Безопасности — поиск уязвимостей

Нисходящее тестирование (Top-Down):

  • Суть: Тестирование начинается с модулей верхнего уровня и постепенно спускается к модулям нижнего уровня
  • Подход: Используются заглушки (stubs) для имитации еще не разработанных модулей нижнего уровня
  • Преимущества: Раннее тестирование основной логики, раннее обнаружение архитектурных проблем
  • Недостатки: Необходимость создания большого количества заглушек, позднее обнаружение проблем на нижних уровнях

Восходящее тестирование (Bottom-Up):

  • Суть: Тестирование начинается с модулей нижнего уровня и постепенно поднимается к модулям верхнего уровня
  • Подход: Используются драйверы (drivers) для вызова тестируемых модулей нижнего уровня
  • Преимущества: Раннее тестирование критичных низкоуровневых модулей, не требуется создание заглушек
  • Недостатки: Необходимость создания драйверов, позднее тестирование верхнеуровневой логики

Сэндвич-стратегия:

Комбинирует оба подхода: тестируются одновременно модули верхнего и нижнего уровней, встречаясь в середине.

Тестирование методом «Черного ящика» — метод функционального тестирования, при котором тестировщик не имеет доступа к внутренней структуре и коду программы.

Основные задачи:

  • Проверка функциональности — соответствие спецификации и требованиям
  • Валидация входных данных — корректная обработка допустимых и недопустимых значений
  • Проверка граничных значений — поведение на границах диапазонов
  • Тестирование интерфейса — взаимодействие между компонентами
  • Верификация выходных данных — правильность результатов

Техники «Черного ящика»:

  • Эквивалентное разбиение — группировка данных в классы эквивалентности
  • Анализ граничных значений — тестирование на границах диапазонов
  • Таблицы решений — проверка комбинаций условий
  • Диаграммы переходов состояний — тестирование переходов между состояниями
  • Попарное тестирование — проверка комбинаций параметров

Тестирование методом «Белого ящика» — метод структурного тестирования, при котором тестировщик имеет полный доступ к исходному коду.

Критерии покрытия:

  • Покрытие операторов (Statement Coverage) — выполнить каждую инструкцию кода хотя бы один раз
  • Покрытие решений/ветвей (Branch Coverage) — протестировать все возможные ветви выполнения
  • Покрытие условий (Condition Coverage) — протестировать все возможные значения каждого условия
  • Покрытие путей (Path Coverage) — выполнить все возможные пути от входа до выхода

Этапы применения:

  • Анализ кода — изучение структуры, построение графа потока управления
  • Определение критериев покрытия — выбор необходимого уровня покрытия
  • Проектирование тестов — создание тест-кейсов для достижения покрытия
  • Выполнение тестов — запуск с инструментами измерения покрытия
  • Анализ результатов — оценка достигнутого покрытия и дефектов

Основные способы:

  • Изолированное тестирование — модуль тестируется отдельно с использованием заглушек (stubs) и драйверов (drivers)
  • Функциональное тестирование модуля — проверка выполнения заявленных функций, входов и выходов
  • Структурное тестирование модуля — покрытие операторов, ветвей, путей, анализ потока данных
  • Тестирование интерфейсов — проверка корректности передачи параметров и возвращаемых значений

Методы:

  • Статический анализ — проверка кода без выполнения (code review, статические анализаторы)
  • Динамическое тестирование — выполнение модуля с тестовыми данными
  • Модульное регрессионное тестирование — повторное тестирование после изменений

Инструменты:

  • Фреймворки модульного тестирования (JUnit, NUnit, pytest, Jest)
  • Инструменты измерения покрытия кода
  • Mock-библиотеки для создания заглушек

По типу:

  • Функциональные ошибки: некорректная реализация, отсутствующая или лишняя функциональность
  • Ошибки обработки данных: некорректная обработка входных данных, неправильная валидация, ошибки в вычислениях
  • Ошибки интерфейса: проблемы UI, взаимодействия между компонентами, API

По серьезности (Severity):

  • Blocker — блокирует работу приложения
  • Critical — критический дефект основной функциональности
  • Major — значительный дефект
  • Minor — незначительный дефект
  • Trivial — тривиальный, косметический дефект

По приоритету (Priority):

  • Immediate — требует срочного исправления
  • High — должен быть исправлен в ближайшем релизе
  • Medium — может быть исправлен позже
  • Low — исправление по возможности

По источнику:

  • Ошибки требований, проектирования, кодирования, тестирования, конфигурации

Структура плана модульного тестирования:

  • Введение: цель, область применения, ссылки на документы, термины
  • Объект тестирования: идентификация модулей, описание функциональности, зависимости
  • Особенности тестирования: перечень тестируемых и нетестируемых функций, подход
  • Критерии прохождения/провала: критерии успешного завершения, приостановки, возобновления
  • Стратегия: выбор метода (белый/черный ящик), критерии покрытия, инструменты
  • Тестовые данные: входные данные, ожидаемые результаты, граничные значения
  • Тестовая среда: требования к оборудованию и ПО, конфигурация
  • Ресурсы: персонал, роли, необходимое обучение
  • График: даты начала и окончания, контрольные точки
  • Риски и меры снижения: идентификация рисков, вероятность, план действий
  • Отчетность: форматы отчетов, частота, получатели

Основные методы локализации:

  • Метод бинарного поиска: разделение кода пополам, определение половины с ошибкой, повторение до локализации
  • Метод обратного прослеживания: начало от точки проявления ошибки, движение назад по цепочке вызовов
  • Метод прямого прослеживания: начало от точки входа, пошаговое выполнение вперед
  • Метод индукции: сбор данных о проявлениях, формулирование и проверка гипотез
  • Метод дедукции: перечисление возможных причин, анализ и устранение невозможных
  • Использование отладчика: точки останова, пошаговое выполнение, просмотр переменных
  • Логирование: добавление операторов вывода, трассировка выполнения
  • Упрощение тестового случая: минимизация входных данных, упрощение условий

Метод структурного тестирования — подход, основанный на анализе внутренней структуры программы, её кода и логики.

Этапы:

  • 1. Построение модели: создание графа потока управления, выделение узлов и ребер
  • 2. Определение критериев покрытия: C0 (операторы), C1 (ветви), C2 (условия), покрытие путей
  • 3. Генерация тестовых путей: выбор путей для требуемого покрытия, определение базового набора
  • 4. Подготовка тестовых данных: входные данные для выбранных путей, расчет ожидаемых результатов
  • 5. Выполнение тестов: запуск с инструментами покрытия, измерение, выявление непокрытых элементов

Метрики:

  • Цикломатическая сложность: V(G) = E - N + 2P
  • Процент покрытия: (Покрытые элементы / Всего) × 100%
  • Плотность дефектов: количество на единицу кода

Тестирование маршрутов — метод, фокусирующийся на проверке различных путей выполнения программы.

Основные понятия:

  • Маршрут — последовательность операторов от входа до выхода
  • Базовый маршрут — независимый путь с новыми ребрами
  • Полный маршрут — путь от входа до выхода программы

Метод базисного пути (Маккейб):

  • Шаг 1: Построение графа потока управления
  • Шаг 2: Вычисление цикломатической сложности V(G)
  • Шаг 3: Определение базового набора путей (количество = V(G))
  • Шаг 4: Подготовка тестовых данных для каждого пути
  • Шаг 5: Выполнение тестов

Вычисление V(G):

  • V(G) = E - N + 2 (ребра - узлы + 2)
  • V(G) = P + 1 (предикатные узлы + 1)
  • V(G) = количество областей графа

Тестирование циклов:

  • Простые циклы: 0, 1, 2, типичное число, максимум итераций
  • Вложенные циклы: от внутренних к внешним
  • Связанные циклы: независимое тестирование

Типы ошибок:

  • Ошибки условных операторов: неправильное условие (!= вместо ==), неполные или избыточные условия
  • Ошибки логических операций: AND вместо OR, неправильные скобки, недостижимые ветви
  • Граничные ошибки: off-by-one (< vs <=), неправильные границы, отсутствие проверки
  • Ошибки переменных: неинициализированные переменные, опечатки, изменение в условии

Причины:

  • Недостатки спецификации: неполное описание, противоречия, неопределенные граничные случаи
  • Ошибки проектирования: неправильная декомпозиция, сложные вложенные условия
  • Ошибки кодирования: опечатки, неправильный приоритет операций, copy-paste
  • Ошибки понимания: неправильная интерпретация требований, незнание особенностей языка

Специфические ошибки:

  • В IF: отсутствие ELSE, пустые блоки, перепутанные ветви
  • В SWITCH/CASE: отсутствие DEFAULT, пропущенные BREAK, перекрывающиеся условия
  • В циклах: неправильное условие выхода, бесконечные циклы

Документируемые результаты:

  • Отчет о тестировании: идентификация модулей, дата, версия кода, конфигурация среды, тестировщик
  • Результаты выполнения: статус (passed/failed/skipped), количественные показатели, время выполнения
  • Метрики покрытия: Statement, Branch, Condition, Function Coverage, список непокрытых участков
  • Обнаруженные дефекты: ID, описание, серьезность, приоритет, шаги воспроизведения, статус
  • Качественная оценка: готовность модуля, стабильность, соответствие требованиям
  • Статистический анализ: плотность дефектов, распределение по типам, тренды
  • Рекомендации: модули для рефакторинга, области риска, предложения по улучшению
  • Артефакты: тест-кейсы, тестовые данные, скрипты, логи, скриншоты

Форматы:

  • Текстовый отчет, HTML с графиками, XML/JSON, Dashboard в CI/CD, презентация

Нагрузочное тестирование — тип тестирования производительности, проверяющий способность системы обрабатывать ожидаемое количество пользователей и транзакций.

Назначение:

  • Проверка работоспособности при нормальной и пиковой нагрузке
  • Определение максимальной пропускной способности
  • Выявление узких мест производительности
  • Оценка времени отклика
  • Проверка стабильности при длительной работе

Этапы:

  • 1. Планирование: определение целей, анализ требований, выбор метрик и инструментов (JMeter, LoadRunner, Gatling)
  • 2. Подготовка среды: настройка окружения, подготовка данных, настройка мониторинга, baseline тестирование
  • 3. Разработка сценариев: создание user scenarios, определение бизнес-транзакций, параметризация
  • 4. Настройка профилей нагрузки: ramp-up, steady-state, peak load, ramp-down
  • 5. Выполнение тестов: smoke test, load test, stress test, endurance/soak test, spike test
  • 6. Мониторинг: время отклика, CPU/память, пропускная способность, база данных, ошибки
  • 7. Анализ результатов: сравнение с требованиями, анализ графиков, идентификация bottlenecks
  • 8. Оптимизация: внесение изменений, настройка конфигурации, повторное тестирование
  • 9. Документирование: отчет, проблемы, рекомендации, baseline метрики

Ключевые метрики:

  • Response Time, Throughput (TPS), Concurrent Users, Error Rate, Resource Utilization

21. Виды функционального тестирования:

  • Unit Testing — тестирование отдельных модулей
  • Integration Testing — проверка взаимодействия модулей
  • System Testing — тестирование системы в целом
  • Acceptance Testing — приемочное тестирование (альфа/бета)
  • Regression Testing — проверка после изменений
  • Smoke Testing — базовая проверка основных функций
  • Sanity Testing — проверка конкретной функциональности

22. Испытание ИС на этапах подготовки к эксплуатации:

  • Предварительные испытания — на тестовой среде, проверка готовности
  • Опытная эксплуатация — в реальных условиях с ограниченным кругом пользователей
  • Приемочные испытания — заказчиком, проверка соответствия требованиям
  • Промышленная эксплуатация — полноценное использование

23. Цели интеграционного тестирования:

  • Проверка взаимодействия между компонентами/модулями
  • Выявление проблем на интерфейсах модулей
  • Проверка передачи данных между компонентами
  • Тестирование интеграции с внешними системами
  • Обнаружение проблем архитектуры

24. Тестирование производительности и сборки:

  • Тестирование производительности: Load, Stress, Endurance, Spike, Scalability testing
  • Тестирование сборки (Build Verification): проверка базовой работоспособности новой сборки, smoke тесты для принятия решения о дальнейшем тестировании

Жизненный цикл дефекта:

  • New — дефект создан тестировщиком
  • Assigned — назначен разработчику
  • Open — разработчик начал работу
  • Fixed — разработчик исправил
  • Pending Retest — ожидает проверки
  • Retest — тестировщик проверяет
  • Verified — исправление подтверждено
  • Closed — дефект закрыт
  • Reopened — появился снова
  • Rejected/Duplicate/Deferred — альтернативные статусы

Отчет дефектов содержит:

  • Идентификация: ID, название, дата, автор, версия ПО
  • Классификация: Severity (Blocker/Critical/Major/Minor/Trivial), Priority (High/Medium/Low), тип, статус
  • Описание: краткое и детальное описание, шаги воспроизведения, ожидаемый vs фактический результат
  • Окружение: ОС, браузер, конфигурация, данные
  • Дополнительно: вложения (скриншоты, логи), связи, комментарии, история
  • Управление: назначено на, целевая версия, компонент, затраченное время

Метрики:

  • Общее количество, распределение по severity/priority/статусам, скорость обнаружения/исправления

26. Назначение тестирования интерфейсов:

  • Проверка взаимодействия между компонентами через интерфейсы
  • Тестирование API (REST, SOAP, GraphQL)
  • Проверка пользовательского интерфейса (UI)
  • Тестирование интерфейсов с базами данных
  • Проверка интеграции с внешними системами

27. Инструментальные средства тестирования:

  • Unit Testing: JUnit, NUnit, pytest, Jest
  • UI Testing: Selenium, Cypress, Playwright, Puppeteer
  • API Testing: Postman, REST Assured, SoapUI
  • Performance: JMeter, LoadRunner, Gatling
  • Mobile: Appium, Espresso, XCUITest
  • CI/CD: Jenkins, GitLab CI, GitHub Actions

28. Принципы интеграционного тестирования:

  • Инкрементальность — постепенное добавление и тестирование компонентов
  • Изоляция — использование заглушек и драйверов для изоляции тестируемых модулей
  • Стратегия интеграции — Top-Down, Bottom-Up, Big Bang, Sandwich
  • Фокус на интерфейсах — особое внимание точкам взаимодействия
  • Раннее начало — интеграционное тестирование начинается параллельно с модульным

29. Особенности для ООП и процедурного программирования:

  • ООП: тестирование на уровне классов, проверка наследования и полиморфизма, интеграция объектов
  • Процедурное: тестирование на уровне функций/процедур, проверка вызовов функций, интеграция модулей

30. Задачи системного тестирования:

  • Проверка системы в целом на соответствие требованиям
  • Тестирование end-to-end сценариев
  • Проверка нефункциональных требований (производительность, безопасность, удобство)
  • Тестирование на целевом окружении
  • Проверка взаимодействия всех компонентов системы

31. Принципы регрессионного тестирования:

  • Непрерывность — выполняется после каждого изменения, встроено в CI/CD
  • Полнота покрытия — проверка критичных функций, измененных и связанных областей
  • Приоритизация — высокий приоритет для критичной функциональности
  • Селективность — выбор тестов на основе анализа изменений (impact analysis)
  • Автоматизация — максимальная автоматизация для быстрой обратной связи
  • Поддержка набора — регулярный пересмотр и обновление тест-кейсов
  • Быстрая обратная связь — минимизация времени выполнения
  • Анализ воздействия — оценка влияния изменений, трассируемость
  • Стабильность — тесты должны быть надежными (не flaky)

34. Цели и задачи регрессионного тестирования:

Цели:

  • Убедиться, что изменения не нарушили существующую функциональность
  • Проверить, что исправления не привели к новым проблемам
  • Подтвердить стабильность системы после модификаций
  • Обнаружить побочные эффекты изменений

Задачи:

  • Повторное выполнение ранее пройденных тест-кейсов
  • Проверка затронутых областей кода
  • Тестирование взаимодействия новых и существующих компонентов
  • Верификация исправленных дефектов
  • Поддержание актуального набора тестов

Виды регрессионного тестирования:

По объему:

  • Полное (Complete) — выполнение всех тестов
  • Частичное (Partial) — подмножество на основе анализа изменений
  • Выборочное (Selective) — по приоритету и риску

По типу изменений:

  • Bug Regression — проверка исправленных багов
  • Conversion/Port — при переносе на другую платформу
  • Configuration — различные конфигурации

По автоматизации:

  • Автоматизированное — с помощью инструментов, в CI/CD
  • Ручное — для сложных сценариев, UI/UX

По времени:

  • Continuous — после каждого изменения
  • Progressive — изменения влияют на спецификацию
  • Corrective — спецификация не меняется

По уровню:

  • Unit, Integration, System, Acceptance Regression

Специализированные:

  • Smoke Regression — базовая проверка
  • Sanity Regression — целенаправленная проверка

32. Издержки тестирования и автоматизация:

  • Издержки: трудозатраты, время выполнения, стоимость инструментов, инфраструктура, обучение
  • Методы автоматизации: инструменты для модульного, UI, API, нагрузочного тестирования; CI/CD интеграция; test frameworks

33. Требования к документации тестирования:

  • Полнота — покрытие всех аспектов тестирования
  • Ясность — понятное изложение для всех заинтересованных сторон
  • Актуальность — соответствие текущему состоянию продукта
  • Структурированность — логичная организация информации
  • Трассируемость — связь с требованиями и кодом
  • Воспроизводимость — возможность повторить тесты по документации

35. Оценки покрытия программы и проекта:

  • Code Coverage: Statement (C0), Branch (C1), Condition (C2), Path Coverage
  • Requirements Coverage: процент покрытых требований тестами
  • Functional Coverage: покрытие функциональности
  • Risk Coverage: покрытие критичных областей
  • Метрики: (Покрытые элементы / Всего элементов) × 100%

36. Преимущества и недостатки автоматизации:

Преимущества:

  • Быстрое выполнение тестов, возможность частого запуска
  • Сокращение трудозатрат в долгосрочной перспективе
  • Повышение покрытия, стабильность результатов
  • Возможность ночного запуска, интеграция с CI/CD

Недостатки:

  • Высокие начальные инвестиции (время, деньги)
  • Требует поддержки и обновления
  • Не заменяет исследовательское тестирование
  • Ложные срабатывания (flaky tests)
  • Не все сценарии можно автоматизировать

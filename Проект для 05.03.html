Основные модели:
  1. Каскадная ( Waterfall ): Строгая последовательность этапов. Переход к следующему этапу только после завершения предыдущего.
  2. V-образная: Развитие каскадной модели, где на каждом этапе разработки закладываются тесты.
  3. Итерационная: Разработка идет "виткам" (итерациями), с постепенным наращиванием функционала.
  4. Спиральная: Акцент на анализе рисков на каждом витке.
  5. Agile (гибкая): Семейство методологий (Scrum, Kanban), фокусирующихся на частых релизах и обратной связи.
Тестирование ПО

Это процесс исследования программного обеспечения с целью получения информации о его качестве, проверки соответствия требованиям и выявления дефектов.

  • Основная цель: Снизить риск отказа ПО при эксплуатации.
  • Проверка соответствия требованиям (Verification).
  • Убедиться, что продукт удовлетворяет нужды пользователя (Validation).
  • Предоставление информации о качестве продукта заказчику.
Качество ПО

Совокупность характеристик программного средства, относящихся к его способности удовлетворять установленные или предполагаемые потребности.

7 основных принципов тестирования (ISTQB):
  1. Тестирование демонстрирует наличие дефектов, а не их отсутствие.
  2. Исчерпывающее тестирование невозможно (нельзя проверить все комбинации).
  3. Раннее тестирование (чем раньше начнешь, тем дешевле исправить).
  4. Скопление дефектов (дефекты часто группируются в определенных модулях).
  5. Парадокс пестицида (тест-кейсы нужно обновлять, иначе они перестают находить баги).
  6. Тестирование зависит от контекста (тестировать сайт и софт для кардиостимулятора нужно по-разному).
  7. Заблуждение об отсутствии ошибок (программа без багов, которая не нужна пользователю — бесполезна).

Тестирование — это неотъемлемая часть ЖЦПП. Современные модели разработки (особенно Agile и V-модель) предполагают, что тестирование начинается параллельно с анализом требований.

  • Связь: Разработка создает продукт, тестирование проверяет его. Тестировщики дают разработчикам обратную связь (баг-репорты). Тестирование требований *до* кодинга предотвращает множество багов.

Это концептуальная схема, описывающая этапы, виды и последовательность действий в процессе тестирования конкретного проекта.

Она тесно связана с выбранной моделью разработки. Например, в V-модели тестирования каждому этапу разработки соответствует свой уровень тестирования (модульное, интеграционное, системное, приемочное).

Статическое тестирование

Это тестирование без запуска программного кода. Оно направлено на поиск багов в документации или в самом коде до его компиляции.

  • Виды: Рецензирование документации (требований, тест-планов), Инспекция кода, Сквозной просмотр (Walkthrough), Статический анализ кода (автоматический).
Динамическое тестирование

Это тестирование, предполагающее запуск программного кода. Проверяется поведение программы в процессе ее выполнения.

  • Позволяет проверить реальный функционал, производительность и взаимодействие компонентов.
  • Примеры: все виды ручного тестирования интерфейса, нагрузочное тестирование, модульные тесты.
  • Верификация (Verification): "Делаем ли мы продукт правильно?" (Compliance to specs). Проверка соответствия этапа разработки требованиям к этому этапу. (Статические методы, модульные тесты).
  • Валидация (Validation): "Делаем ли мы правильный продукт?" (Fitness for purpose). Проверка того, что созданный продукт соответствует нуждам пользователя. (Динамические методы, приемочное тестирование).
Тест-план

Это документ, описывающий весь объем работ по тестированию. Это "генеральная стратегия" для тестировщиков.

  • Что тестируем? (Объект).
  • Как тестируем? (Стратегия, методы).
  • Кто тестирует? (Ресурсы).
  • Где тестируем? (Окружение).
  • Критерии начала и окончания тестирования.
Тест-кейс

Это минимальный набор действий и условий, необходимых для проверки конкретной функции ПО.

  • Структура: Айдишник, Заголовок, Предусловия, Шаги воспроизведения, Тестовые данные, Ожидаемый результат.
  1. Модульное (Unit): Проверка отдельных минимальных компонентов кода (функций, классов).
  2. Интеграционное (Integration): Проверка взаимодействия между объединенными модулями.
  3. Системное (System): Проверка всей системы целиком на соответствие исходным требованиям.
  4. Приемочное (Acceptance): Финальное тестирование, проводимое заказчиком или конечными пользователями.
Основное деление (по цели):
  • Функциональное: "Что делает программа?" (функциональность, совместимость).
  • Нефункциональное: "Как хорошо она это делает?" (производительность, удобство использования, безопасность, надежность).

Это деление на более узкие задачи тестирования.

  • Дымовое тестирование (Smoke): Поверхностная проверка ключевых функций после сборки.
  • Регрессионное тестирование: Повторное тестирование после изменений, чтобы убедиться, что старый функционал не сломался.
  • Санити тестирование (Sanity): Глубокая проверка конкретного исправленного баг-репорта.
  • UI Тестирование: Тестирование пользовательского интерфейса.
  • Белый ящик (White Box): Тестировщик знает внутреннее устройство кода. Тесты пишутся на основе структуры кода. (Пример: Unit-тесты).
  • Черный ящик (Black Box): Тестировщик не знает код, видит систему только "снаружи". Тесты пишутся на основе требований. (Пример: Тестирование интерфейса).
  • Серый ящик (Grey Box): Комбинация методов. Тестировщик имеет частичный доступ к коду или БД.
Тест-дизайн

Это процесс проектирования тест-кейсов. Техники помогают создать эффективные тесты с минимальным покрытием.

  1. Эквивалентное разделение: Разбиение данных на классы, где один представитель заменяет весь класс.
  2. Анализ граничных значений: Тестирование на границах и рядом с границами диапазонов данных.
  3. Таблицы принятия решений: Удобно для тестирования сложной логики.
  4. Диаграмма переходов и состояний: Для систем, где поведение зависит от состояния.

Дефект (Bug, Error)

Это несоответствие фактического результата Ожидаемому результату, описанному в требованиях.

Ключевые атрибуты баг-репорта:
  • ID: Уникальный номер.
  • Заголовок (Summary): Краткое описание (Что, Где, При каких условиях).
  • Шаги воспроизведения: Пошаговая инструкция, как получить баг.
  • Серьезность (Severity): Влияние бага на бизнес-логику системы.
  • Приоритет (Priority): Срочность исправления.
  • Фактический и Ожидаемый результаты.
Жизненный цикл дефекта:

Это путь дефекта от момента обнаружения до закрытия.

  • New (Новый): Только что создан тестировщиком.
  • Assigned (Назначен): Менеджер передал баг разработчику.
  • Fixed (Исправлен): Разработчик исправил код.
  • Verified (Проверен): Тестировщик подтвердил исправление.
  • Closed (Закрыт): Финальный статус.
  • Rejected (Отклонен): Если это не баг.
  • Deferred (Отложен): Будет исправлен позже.

Это процесс создания баг-репорта в специальных системах (Баг-трекерах, например, Jira, YouTrack). Качественно задокументированный дефект экономит время разработчика и ускоряет релиз.

Автоматизированное тестирование

Это использование программного обеспечения для выполнения тестов и сравнения фактического результата с ожидаемым. Пишутся скрипты (код).

  • Зачем: Ускорение тестирования, избавление от рутины, возможность частых прогонов (например, при CI/CD).
  • Инструменты: Selenium, Cypress, Playwright (для веба), Postman (для API).

Проверка характеристик, не связанных с бизнес-логикой. Описывает качество работы системы.

  • Тестирование производительности (Скорость ответа, устойчивость).
  • Тестирование безопасности (Защита от взломов, утечек данных).
  • Тестирование удобства использования (Usability): Насколько интерфейс понятен пользователю.
  • Смоук-тестирование: Базовая проверка работоспособности.
  • Тестирование критического пути: Проверка самых частых сценариев пользователя.
  • Расширенное тестирование: Покрытие всех функций системы.

  • Нагрузочное: Проверка работы под нормальной нагрузкой.
  • Стресс-тестирование: Проверка работы под критической нагрузкой.
  • Объемное: Проверка работы с большими объемами данных.
  • Тестирование совместимости (кроссбраузерность).
  • Дымовое (Smoke): Проверка самого критического функционала (например, можно ли залогиниться на сайт). Цель: Быстро понять, жива ли сборка.
  • Регрессионное (Regression): Глубокая проверка всей системы после любого изменения кода. Цель: Убедиться, что изменения не сломали старое.
  • Альфа-тестирование: Проводится внутри компании разработчиков. Обычно это приемочное тестирование для внутреннего релиза.
  • Бета-тестирование: Проводится конечными пользователями (бета-тестерами) за пределами компании. Помогает получить реальную обратную связь.
Нагрузочное тестирование (Performance Testing)

Определение времени отклика, пропускной способности и устойчивости ПО под ожидаемой нагрузкой.

  • Методы: Эмуляция пользователей, генерация трафика.
  • Инструменты: Apache JMeter, Gatling, K6.
Интеграционное тестирование (Integration Testing)

Проверка взаимодействия между отдельными программными модулями, которые уже прошли модульное тестирование.

  • Ищет баги в интерфейсах обмена данными.
  • Примеры: тестирование API, тестирование связок БД + Код.
Модульное тестирование (Unit Testing)

Тестирование наименьших компонентов программы (отдельных функций, методов, классов).

  • Это метод "Белого ящика". Пишется разработчиками.
  • Цель: Быстро найти ошибки в логике функции.

V-модель наглядно показывает, что каждому этапу разработки соответствует уровень тестирования.

  • Анализ требований -> Приемочное тестирование.
  • Проектирование системы -> Системное тестирование.
  • Детальное проектирование -> Интеграционное тестирование.
  • Кодирование -> Модульное тестирование.
Тестовое окружение (Test Environment)

Совокупность аппаратного, программного обеспечения и сетевых настроек, необходимых для выполнения тестов. (Пример: "Стенд тестирования").

Процесс тестирования (кратко):
  1. Планирование (Test Plan).
  2. Тест-дизайн (Test Cases).
  3. Подготовка окружения.
  4. Выполнение тестов.
  5. Анализ результатов и заведение баг-репортов.
  6. Отчет о результатах.

В Agile (Scrum) тестирование начинается с первого дня спринта. Нет жесткого отделения тестировщиков от разработчиков — это единая команда.

  • Тестировщики активно участвуют в грумингах требований.
  • Автоматизация тестирования критически важна для частых релизов.

Процесс управления командой, ресурсами и документацией тестирования.

  • Инструменты для баг-трекинга: Jira, Mantis.
  • Инструменты для хранения тест-кейсов (TMS): TestRail, Zephyr (плагин для Jira), Allure TestOps.
Ключевые аспекты:
  • Кроссбраузерность.
  • Адаптивность (мобильные устройства).
  • Тестирование веб-служб (API, JSON/XML).
  • Производительность (время загрузки страниц).
Ключевые аспекты:
  • Совместимость с ОС (Windows 10/11, macOS, Linux).
  • Установка/Удаление/Обновление.
  • Потребление ресурсов системы (ОЗУ, Процессор).
  • Взаимодействие с периферией.
Ключевые аспекты:
  • Проверка прерываний (звонок, СМС, низкий заряд).
  • Разные ориентации экрана.
  • Работа с разными типами сетей (2G/3G/4G/WiFi).
  • Установка из сторов (App Store, Google Play).
Метрики

Это численные показатели качества. (Примеры: % пройденных тестов, плотность багов, время исправления багов).

Отчётность (Test Report)

Итоговый документ, подытоживающий результаты тестирования сборки. Отвечает на вопрос: "Можно ли выпускать продукт?"

Риск-ориентированное тестирование (Risk-based Testing)

Стратегия, при которой тестирование фокусируется на наиболее критичных и рискованных зонах приложения.

  • Позволяет эффективно тратить время, если сроки сжаты.
  • Приоритет тестов определяется формулой: Риск = Вероятность ошибки * Ущерб от ошибки.
